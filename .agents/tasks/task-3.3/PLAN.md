## 6. Questions & Decisions for Human Approval

### a. Question
How should we format the parameter descriptions to ensure FastMCP picks them up for the JSON Schema while respecting the specifications?

### b. Brief Background
The `SPECIFICATIONS.md` dictates specific flat function signatures for the 5 tools (e.g., `def search_regulatory_docs(query: str, ...)`). However, the `mcp-builder` skill (specifically `python_mcp_server.md`) recommends encapsulating parameters into Pydantic `BaseModel` classes for strict validation and using `Field(description=...)`. Doing so would change the signature to `def search_regulatory_docs(params: SearchInput)`. FastMCP natively supports both standard Python type hints (where it parses parameter docstrings) and Pydantic models.

### c. Options with Recommendation
- **Option 1 (Recommended)**: Retain the flat function signatures from `SPECIFICATIONS.md` but use `typing.Annotated` with `pydantic.Field` (e.g., `query: Annotated[str, Field(description="...")]`) combined with detailed Google-style docstrings. This achieves strict schema validation and rich LLM descriptions without mutating the expected interface.
- **Option 2**: Refactor the tool parameters into explicit Pydantic `BaseModel` classes (e.g., `SearchRegulatoryDocsInput`) as suggested by the Python MCP guide.
- **Option 3**: Use plain Python type hints and rely solely on FastMCP's internal docstring parser to populate the JSON Schema descriptions.

### d. Justification of the Recommendation
Option 1 provides the best of both worlds: it leverages Pydantic's robust metadata and validation capabilities (which FastMCP processes seamlessly) while keeping the exact function signatures mandated by `SPECIFICATIONS.md`. It avoids the boilerplate of creating 5 distinct input model classes for tools that only have a few parameters.
